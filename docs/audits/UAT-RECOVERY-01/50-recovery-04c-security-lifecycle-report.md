## G. O-15 recommended remedy (design only; nothing implemented or created)
Approved principles: (1) `project.update` ≠ authority to appoint a PM; (2) no self-claim of a PM-less project; (3) PM assignment needs independent authority; (4) no implicit System Admin bypass; (5) tenant-bound; (6) auditable before/after; (7) no automatic backfill.
| Option | (1) | (2) | (3) | (4) | (6) | (7) | Verdict |
|---|---|---|---|---|---|---|---|
| **B** keep today's rule | ✗ | ✗ | ✗ | ✗ (admin re-acquires authority) | ✗ | ✓ | rejected — violates the approved principles |
| **C** forbid `pm_id` in the generic update | ✓ | ✓ | needs an alternative path | ✓ | ✓ if the new path audits | ✓ | incomplete alone (there must be an independent assignment path) |
| **A** creator sets the first PM; later changes need the current PM **or** an independent permission | ✓ | ✓ | ✓ | ✓ (no grant by default) | ✓ | ✓ | **recommended, in its minimal form below** |
**Minimum coherent design ("A-minimal")**
1. *Canonical decision* — new `ProjectPmAssignment::allows()` (the S4b helper): unchanged value ⇒ allow; otherwise require **same tenant** AND (**actor is the current PM** (hand-over) OR **actor holds `project.assign_manager`**) AND the new PM belongs to the project's tenant. The S4b branch "project has no PM ⇒ any `project.update` holder may set it" is **removed**. `project.update` stays the gate for metadata only. Project **creation** keeps allowing the creator (`project.create`) to name the first PM (same tenant).
2. *Permission* — no existing permission has these semantics (`project.update`, `user.manage_roles`, `role.assign` are different decisions), so one new canonical code is required: **`project.assign_manager`** (module `project`, action `assign_manager`; dotted style like the rest of the `project.*` family). Seeded as a *definition only* (like the S1 catalog-only rows) and **granted to no role by the seed**; the Owner decides which role receives it (candidate: System Admin as an explicit, auditable, tenant-bound grant — which is a permission, not an implicit bypass). This round does **not** create or grant it.
3. *Authorised actors* — current PM of that project; any user holding `project.assign_manager` in the same tenant. Nobody else (not Member, not other PMs, not System Admin without the grant).
4. *Operations authorised* — first appointment of a PM-less project, replacement, and clearing of `pm_id`, via the project update endpoints (API + web) and the bulk project-update path; no new endpoint is needed.
5. *Audit* — event `project.manager.changed` in `audit_logs` (`entity_type=project`, `entity_id`, `tenant_id`, actor `user_id`, `old_data={pm_id}`, `new_data={pm_id}`, `route`, `ip`), written in the same transaction as the update; failure to audit aborts the change.
6. *Migration / backfill* — no schema change. **No automatic assignment** of existing PM-less projects. Provide a read-only report command (dry-run, per tenant) listing PM-less projects; adoption is a per-project, audited action by a `project.assign_manager` holder. Until adopted, PM-less projects have no task-management authority except assignees (already the S4 behaviour) — a temporary administrative burden, not a security gap.
7. *Compatibility* — existing `pm_id` values untouched; hand-over by the current PM keeps working; web edit form should render the PM field only for actors allowed to change it and omit it otherwise (omitted ⇒ unchanged, already supported).
8. *Regression tests* — turn the 3 RED tests GREEN; keep the 3 guards; add: holder of `project.assign_manager` (granted **in the test** to a role as an explicit fixture) may appoint within the tenant and is denied cross-tenant; non-holder PM-less claim denied on API, web, bulk; creator names first PM on create; audit row has before/after; the S4b test `…unmanaged_project_pm_can_be_set_by_a_project_update_holder…` and the O-15 characterisation tests change deliberately (documented) because the claim path is removed.
9. *Rollback* — revert the helper change; leave the (ungranted) permission row and audit rows; no data to restore.
**Owner decisions needed:** approve the permission name/semantics; decide who receives it (and whether System Admin); approve the adoption procedure for legacy PM-less projects.

## H. Backup test filesystem risk and isolation proposal (read-only analysis; no production Backup change; nothing deleted)
**ENVIRONMENT_RISK_CONFIRMED.** (Observed after R1/R2: `storage/backups` now holds two `backup_<date>_<time>.sql` files created at the start of R1 and R2 by a test that was *not* excluded from R2 — source test not identified; they were left untouched. Four test classes execute the real `backup:run`: `Console\BackupRetentionTest`, `Console\BackupContentsSafetyTest`, `Console\BackupStorageLocationTest`, `BackupCommandTest`. They target the **real** `storage/backups` (`clean()` deletes `backup_*` there — a developer's genuine backups in that folder would be removed), copy the real `storage/app` + `storage/logs` (≈ 650 MB) into it, then `tar -czf` via `Process::run` (default 60 s timeout, ~1.5–3 min per run). The disk is **100 % full (2.0–2.6 GiB free)**; a full run needs ~1.3 GB scratch. `BackupContentsSafetyTest` creates a sentinel `.env`/`.env.gap054probe` in the repo root only if absent and removes only what it created (the real `.env` is not overwritten while it exists). My interrupted run in the previous round left a partial `backup_full_*` directory, a 23 MB `.tar.gz` and three 0-byte fixture archives in `storage/backups` (git-ignored, test-owned); they were *not* deleted by me and the tests' own `clean()` removed them in the next run. **Exact cause of each historical failure: INCONCLUSIVE** (the tests assert only the exit code); disk pressure + size-dependent timing + live-workspace coupling are the supported hypotheses.
**Path audit for `$this->app->useStoragePath($tmp)`:** `BackupCommand` (`storage_path('backups')`, `storage_path('app')`, `storage_path('logs')`, staging dir, tar source/dest) and `BackupArchiveStore` (`stagingRoot()`, `typedArchives()` glob, `delete()` `unlink`, `localPathsExcludedFromFileBackups()`) all resolve through `storage_path()` at call time ⇒ they follow the override. No config cache exists (`bootstrap/cache` holds only `packages.php`/`services.php`). With `backup.disk = null` (all tests set it) the `filesystems.disks.*.root` absolute paths captured at boot are never read. Database step is the **fallback text dump** under SQLite (no DB file copied; MySQL path unused). `public_path('uploads')` does not exist. **Escapes that remain (read-only / not backup targets):** `base_path('composer.json'|'composer.lock')` copied *from* the repo (small); the log channel path (`laravel.log`) is fixed at boot and is written by logging, not by the backup; the `.env` sentinel logic in `BackupContentsSafetyTest` uses `base_path()` and must be kept guarded ("create only if absent, remove only what the test created").
**Separate fixture-only repair proposal (not implemented, not mixed with S4c):** a shared trait `UsesIsolatedBackupStorage`: in `setUp()` create `$tmp = sys_get_temp_dir().'/zena-backup-fixture-'.bin2hex(random_bytes(6))` with `app/`, `logs/`, `framework/`, `backups/` containing a few KB of synthetic files; call `$this->app->useStoragePath($tmp)`; **abort the test** unless `str_starts_with(realpath(storage_path()), realpath(sys_get_temp_dir()).'/zena-backup-fixture-')` and `storage_path('app')` is inside it; skip when free disk < 200 MB; `config(['backup.disk'=>null])`. `tearDown()` removes **only** `$tmp` after re-verifying that prefix (never `storage/backups`). Replace the repo-wide secret sentinel with sentinels inside `$tmp/app`; keep the `.env` sentinel guard or move that assertion to a temp base path. Result: no 650 MB traversal, no real `storage/backups`, deterministic <5 s runs, no 60 s timeout exposure. Preconditions before any destructive Backup test is run again: this trait in place and verified by a test that fails if `storage_path()` is not the temp directory.
