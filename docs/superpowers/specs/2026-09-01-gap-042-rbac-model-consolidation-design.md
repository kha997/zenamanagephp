**Migration design (schema/migration category of §13a, not created in this Gate 2, unchanged from Round 1):** mirror `database/migrations/2026_02_02_020000_create_project_user_roles_table.php`'s shape — the closer sibling match, since `UserRoleCustom` (like `UserRoleProject`, unlike `UserRoleSystem`) uses `HasUlids`' default single `id` primary key (not a composite `[user_id, role_id]` key) and a plain nullable `deleted_at` column (not the `$table->softDeletes()` trait column `UserRoleSystem`'s migration uses):

```
Schema::create('custom_user_roles', function (Blueprint $table) {
    $table->ulid('id')->primary();
    $table->ulid('user_id');
    $table->ulid('role_id');
    $table->timestamps();
    $table->timestamp('deleted_at')->nullable();

    $table->index(['user_id']);
    $table->index(['role_id']);
    $table->foreign('user_id')->references('id')->on('users')->onDelete('cascade');
    $table->foreign('role_id')->references('id')->on('roles')->onDelete('cascade');
});
```

No `tenant_id` column — tenant scoping flows transitively through the assigned `role_id`'s own `roles.tenant_id` (§6), matching `project_user_roles`' pattern (which also carries no `tenant_id`, scoping instead through `project_id`→`projects.tenant_id`). `down()` must `dropIfExists('custom_user_roles')`, matching every sibling migration's pattern (§13).

## 2e. Route-parameter vs. request-body identity — explicit Gate-2 decision (new, Round 2)

**Finding:** `POST /api/v1/rbac/assignments/users/{user}/roles` → `AssignmentController::assignUserRoles(Request $request)`. The method signature takes only `Request $request` — no `$userId` parameter — so the route's `{user}` URL segment is never bound to anything and is silently discarded by Laravel's router (a route parameter with no matching method parameter is simply not injected; this is not an error). The method instead reads `user_id` exclusively from the validated request body (`$request->validate(['user_id' => 'required|string', ...])`). **Today, these are two completely independent, never-cross-checked identities** — a caller can `POST /assignments/users/AAAA/roles` with body `{"user_id": "BBBB", ...}` and the assignment silently applies to `BBBB`, not `AAAA`. This is a genuine contract/security defect: any caller or audit-log expectation that trusts the URL to describe which user is being modified is wrong.

**Decision: the route parameter is authoritative.** Implementation must bind `assignUserRoles(Request $request, string $user): JsonResponse` (adding the `$user` parameter so Laravel injects the route segment), use `$user` as the target user id, and either (a) ignore any `user_id` present in the request body entirely, or (b) — the safer, fail-closed choice, adopted here — reject the request with HTTP 400 if the body supplies a `user_id` that does not match the route `{user}` segment, so a caller sending inconsistent data gets an explicit error rather than a silent, surprising redirect to a different user. This mirrors the standard REST convention (the URL identifies the resource being acted on) and removes the dual-identity ambiguity by construction, not by trusting callers to always agree.

**Applied to every other in-scope assignment route, checked individually — no other route has this specific defect:**
- `DELETE /api/v1/rbac/assignments/users/{user}/roles/{role}` → `AssignmentController::removeUserRole(string $userId, string $roleId)` — both identities already come from route parameters, positionally bound correctly (route order `{user}`, `{role}` matches method parameter order `$userId`, `$roleId`). No body identity exists to conflict. **No change needed.**
- `POST /api/v1/rbac/user-roles` → `assignUserRoles(Request $request)` (the second route mounted to the same method, no path parameters at all) — body `user_id` is the *only* identity source; there is no route parameter to conflict with. **No change needed** — this route's contract is already internally consistent (though it shares the same handler as the `{user}`-parameterized route above; implementation must ensure adding a `$user` parameter to the shared method signature does not break this second, parameter-less route — e.g. by making the new parameter optional/nullable and falling back to the body when absent, or by giving each route its own thin wrapper. Not designed further here — an implementation-time decision within this explicit contract).
- `DELETE /api/v1/rbac/user-roles/{user}/{role}` → `removeUserRole(string $userId, string $roleId)` — same as the `assignments/` DELETE route above, route-parameter-only, already consistent. **No change needed.**
- `POST /api/v1/rbac/bulk-assign-roles` → `RBACController::bulkAssignRoles()` — no path parameters in this route at all (`user_ids`/`role_ids` arrays come from the body only). **No conflict, no change needed** (its actual defect is §2a #3, unrelated to identity reconciliation).
- The three category-C `assignments/projects/*` routes (§2c) — undefined target methods today, so there is no existing contract to reconcile; **if** a future, separately-authorized implementation adds the missing methods, they must consume `{project}`/`{user}` from route parameters as authoritative, matching this same decision, not repeat the request-body pattern this section corrects.

Both model pairs' underlying tables originate from the **same** migration (`zena_roles`/`zena_permissions` were `Schema::rename()`d to `roles`/`permissions`, not recreated) — the columns are, and always have been, physically identical except for one later addition:

|---|---|---|---|
| | `name`, `scope`, `allow_override`, `description` | `name`, `scope`, `allow_override`, `description`, `is_active`, `tenant_id` | `id`, `name` (unique), `scope`, `allow_override`, `description`, `is_active`, `tenant_id`, timestamps |

| | `code`, `module`, `action`, `description` | `code`, `name`, `module`, `action`, `description` | `id`, `code` (unique), `module`, `action`, `description`, `is_active`, `name` (nullable, added `2026_01_30_000001_add_name_to_permissions_table.php`), timestamps |

`Src\RBAC\Models\Role`'s fillable set is a strict subset of `App\Models\Role`'s; same for `Permission`. Both `Permission` classes auto-generate `code` from `module`+`action` on create when empty (`Src\RBAC\Models\Permission::boot()` vs. the equivalent in `App\Models\Permission::boot()`) — identical behavior, independently implemented twice.

Pivot tables: `zena_role_permissions`→`role_permissions` and `zena_user_roles`→`user_roles` are the same rename pattern — `role_id`, `permission_id`/`user_id`, `allow_override` (role_permissions only), timestamps, composite primary key. No migration has altered `role_permissions`' or `user_roles`' columns since the rename (confirmed: only `permissions` received a post-rename column addition, per §2's migration grep). **Conclusion: the schemas are behaviorally compatible by construction — they are the same tables under different historical names, not two independently-evolved schemas that happen to look similar.**

One material behavioral difference found, not a schema difference: `RoleController::store()` (`src/RBAC/Controllers/RoleController.php:96-101`) never sets `tenant_id` on `Role::create()`, and its duplicate-name check (`Role::where('name', ...)->where('scope', ...)->exists()`) is not tenant-scoped either — role names are currently unique **globally**, not per-tenant, in the `Src\RBAC` module's own logic. This is not a regression risk from convergence — `App\Models\Role`'s `roles` table already carries the same global `roles_name_unique` index (confirmed in the rename migration, §3 of the Gate-1 evidence) — but it means neither model pair enforces per-tenant role-name uniqueness today. Convergence does not need to fix this (out of the approved boundary; flagged as a pre-existing, shared characteristic, not something Option A/B/C changes for better or worse).

## 4. Options comparison

### Option A — Converge onto canonical `roles`/`permissions`/`role_permissions`/`user_roles` (via `App\Models\Role`/`Permission`, or `Src\RBAC` classes repointed to the same tables)

**Mechanism:** Either (a) delete `Src\RBAC\Models\Role`/`Permission` and have `src/RBAC/Controllers/*`/`RBACManager`/`PermissionMatrixService` use `App\Models\Role`/`Permission` directly, or (a′) keep the `Src\RBAC\Models\Role`/`Permission` class names (so no `use` statement churn across 9+ consumer files) but change `protected $table` from `zena_roles`/`zena_permissions` to `roles`/`permissions`, and change the two hardcoded pivot-table strings in `Role::permissions()`/`Permission::roles()` from `zena_role_permissions` to `role_permissions` (already what `Src\RBAC\Models\RolePermission` — currently dead — declares). `UserRoleSystem`/`UserRoleCustom`/`UserRoleProject`'s `role()` relation needs no change if `Role::class` still resolves within `Src\RBAC\Models` — it would just point at the now-repointed table.

**Pros:** Zero new tables, zero new migrations for `Role`/`Permission`/`role_permissions`/`user_roles` (schema already exists, already seeded, already the live source of truth for the `rbac:` authorization gate itself). Smallest possible diff — 2 model files' `$table`/pivot-string values, no controller/service logic changes required (fillable subset means no field ever gets silently dropped). Immediately closes the split-brain: one authoritative table set, used by both the authorization gate and the business logic behind it. Matches the already-existing-but-dead `RolePermission` pivot model's stated intent.

**Cons:** `Src\RBAC\Models\Permission`'s fillable (`code, module, action, description`) omits `name`, which `App\Models\Permission`'s callers may rely on being settable; since `permissions.name` is nullable (added later, per §3), this is a non-breaking gap, not a conflict — existing `Src\RBAC`-created rows simply leave `name` null, exactly as `PermissionSeeder`'s own rows already sometimes do (this is the AUD-28 pattern GAP-044 already documented, not a new risk). `custom_user_roles` needs its own migration regardless of this option — resolved at §2b, not a cost specific to Option A.

### Option B — Thin compatibility/adapter layer, `Src\RBAC` classes/API preserved as-is against the standard schema

**Mechanism:** Same table repointing as Option A, but additionally wrap `Src\RBAC\Models\Role`/`Permission` in an explicit adapter (e.g., extend `App\Models\Role`/`Permission` instead of `Illuminate\Database\Eloquent\Model` directly, remapping the narrower `Src\RBAC` fillable/constant surface — `Role::VALID_SCOPES`, `Permission::generateCode()` — onto the parent).

**Pros:** Slightly more explicit "this is the same underlying entity, different historical API" statement in code; a single class hierarchy point if the two APIs need to diverge again later for some reason.

**Cons:** More moving parts than Option A for no behavioral difference given §3's finding that the fillable sets are already a strict subset — inheritance adds a coupling axis (any future change to `App\Models\Role` silently propagates to `Src\RBAC\Models\Role`) without buying anything Option A's direct table-repoint doesn't already achieve. Effectively Option A with extra indirection; **not recommended as a separate mechanism** unless Gate 2 review surfaces a concrete reason the two APIs must diverge.

### Option C — Retire/de-duplicate `Src\RBAC` model/service path entirely, route `/api/v1/rbac/*` through `App\Models\Role`/`Permission` directly

**Mechanism:** Delete `Src\RBAC\Models\Role`/`Permission`/`RolePermission`; rewrite the 5 controllers + `PermissionMatrixService` to use `App\Models\Role`/`Permission` and `App\Models\User::roles()`/`hasPermission()` instead of `RBACManager`'s 3-layer computation; decide the fate of `RBACManager`'s system/custom/project layering (either port it to operate against `App\Models\Role` + the existing `system_user_roles`/`project_user_roles` tables plus a new `custom_user_roles` migration, or drop the 3-layer model in favor of `App\Models\User`'s flat `roles()`/`hasPermission()`).

**Pros:** Eliminates the duplicate class hierarchy entirely — no `Src\RBAC\Models\Role` vs `App\Models\Role` naming confusion for future readers. Removes the now-dead `App\Http\Controllers\{RoleController,PermissionController,AssignmentController,RBACController}` / `App\Services\{RBACManager,PermissionMatrixService}` orphan-duplicate question too, if folded into the same cleanup (though that cleanup is explicitly **not** part of GAP-042's approved boundary, per Gate 1 — see §7).

**Cons:** By far the largest diff of the three — touches every consumer file's imports and internals, not just 2 models' table pointers; the 3-layer System/Custom/Project permission-override model (`RBACManager::computeEffectivePermissions()`, §2 of the Gate-1 evidence, §2 above) is materially richer than `App\Models\User`'s flat `hasRole()`/`hasPermission()` (least-privilege intersection across layers, `allow_override` per layer) — collapsing it to the flat model is a **behavior change**, not a bug fix, and is exactly the kind of business-semantics decision the repository's Design Dependency Preflight exists to catch (§7). Rewriting 5 controllers + a service class carries materially more regression risk than repointing 2 `$table` properties, for a benefit (naming clarity) that Option A's dead-code note (`RolePermission` already unused) shows can be achieved incrementally later without forcing the whole rewrite now.

### Legacy-compatibility-table/view variant (evaluated, not recommended)

Recreating `zena_roles`/`zena_permissions` as either permanent duplicate tables (kept in sync with `roles`/`permissions` via triggers/observers) or database views over `roles`/`permissions` was evaluated per the Owner's explicit request to consider it. **Not recommended:**
- A duplicate table reintroduces exactly the split-brain authority problem Gate 1 diagnosed (two tables, one truth, requiring a sync mechanism that can itself drift) — the opposite of the Owner's stated goal ("establishing ONE authoritative RBAC data model... Avoid split-brain RBAC data").
- A read-only view could serve `SELECT`-only consumers, but `Src\RBAC\Controllers\RoleController::store/update/destroy`, `PermissionController::store/update/destroy`, and `RBACManager`'s role-assignment methods (§2) all write — a view does not support arbitrary writes back to a renamed base table without additional (and MySQL-version-sensitive) `INSTEAD OF`-trigger machinery Laravel's schema builder does not manage, adding operational complexity with no compatibility benefit Option A doesn't already provide directly.
- No consumer in the approved boundary (§2) requires the literal string `zena_roles`/`zena_permissions` to exist for any reason other than that being the currently-hardcoded (and broken) table name — i.e., nothing needs the *name* `zena_roles`, only working Role data. A compatibility shim solves a problem no live consumer actually has.

### Recommendation: **Option A** (direct table repoint, keeping `Src\RBAC\Models\Role`/`Permission` class names to minimize consumer-file churn)

Rationale: §3 establishes the schemas are the same tables historically, not independently-evolved ones — there is nothing to "adapt" (Option B) or "port behavior across" (Option C) that Option A's direct repoint doesn't already carry for free, because the fillable/relationship surface is already a compatible subset. Option C's larger rewrite is justified only if the Owner separately decides to collapse the 3-layer permission model into the flat one — a business-semantics decision this Gate 2 does not make (§7) and that the Gate-1-approved boundary did not ask for. Option A is reversible (§13), requires no new migration for the primary defect (§11), and directly satisfies "avoid split-brain" by making `roles`/`permissions` the single table set for both the authorization gate and the business logic behind it, on day one. (§2a's contract fixes and §2b's `custom_user_roles` migration and §6's tenant-scoping design are additional, separately-tracked work items within the same approved boundary — see §13a — not alternate options to Option A itself.)

## 6. Tenant isolation and tenant_id semantics — corrected, explicit fail-closed design (Round 3)

**Revision note (Round 3).** Two corrections to this section: (a) the visibility predicate `whereNull('tenant_id')->orWhere('tenant_id', $tenantId)`, as written in Round 1/2, is an **unsafe, non-composable fragment** — appended to any further `where(...)` call (e.g. `->find($id)`, `->where('scope', ...)`), PHP/Eloquent's left-to-right `orWhere` chaining produces SQL boolean precedence `tenant_id IS NULL OR (tenant_id = ? AND <other filter>)`, not the intended `(tenant_id IS NULL OR tenant_id = ?) AND <other filter>` — the first form can return **another tenant's global-looking row combinations or fail to exclude rows correctly** once a second predicate is chained after it, because `OR` binds looser than `AND` and the un-grouped fragment leaks past its intended boundary. Every occurrence below is corrected to an explicitly grouped predicate. (b) Round 1/2 let the tenant-scoped surface **create and mutate** global (`tenant_id IS NULL`) roles — this is corrected to **read-only** for global roles through this surface (full policy in the new "Create/update/delete/sync — global-role read/write policy" subsection below).

**Why this could not stay deferred.** `tenant.isolation` middleware (`app/Http/Middleware/TenantIsolationMiddleware.php`) only establishes *authenticated tenant context* (`$request->attributes->set('tenant_id', ...)`) — it does not automatically scope any model query. Every `/api/v1/rbac/*` route additionally runs `rbac:<code>` (`RoleBasedAccessControlMiddleware`), which only checks *whether the user holds a named permission* — it never inspects *which row* a request targets. Neither middleware bounds `Role::query()`, `Role::find($id)`, or `Role::where(...)` to the caller's own tenant. **Today, on current `main`, this is unreachable — every such query 500s before returning any row, because the table doesn't exist.** Once Option A repoints the table, these same queries **succeed** against real, tenant-owned data — so the cross-tenant exposure becomes newly, actually reachable for the first time. This is exactly the case the Owner's correction identifies: fixing the table-name defect without fixing the scoping would trade an availability defect for a confidentiality defect.

**Intended semantics, traced from evidence (not invented):**
- `roles.tenant_id` is nullable. `RoleSeeder`'s `system`-scope roles (the only roles any production code path has ever created — confirmed by `grep -rn "Role::create\|Role::firstOrCreate"` across `app/`, `src/`, `database/`, none of which ever sets `tenant_id`) are created with `tenant_id` left `null`. This is decisive evidence for the intended meaning: **`tenant_id IS NULL` = global/system role, visible to and usable by every tenant; `tenant_id = <id>` = a role owned by exactly that tenant** (the `custom`/`project` scopes' evident purpose, per `Role::VALID_SCOPES` and `RoleController::store()`'s validation, even though no code has yet exercised non-null `tenant_id` in practice).
- `RBACController::getRolesByScope()` (`src/RBAC/Controllers/RBACController.php:128`) already implements a *partial* version of this: `if ($tenantId) { $query->where('tenant_id', $tenantId); }` — evidence the tenant-scoping intent already exists in this exact codebase, inside the approved boundary, just inconsistently applied (only this one of the module's several list/read paths does it, and even this one has a related, narrower gap noted below). `permissions` has no `tenant_id` column in either schema — permissions remain global/module-scoped in both systems, unchanged by this design.
- **A related, narrower gap in the existing partial implementation, noted but not the primary fix target:** `getRolesByScope()`'s filter, as written, is `WHERE tenant_id = ?` when a tenant is present — under standard SQL null semantics this *excludes* global (`tenant_id IS NULL`) system roles once any tenant context is set, an under-inclusive visibility gap (a tenant using this endpoint currently cannot see system roles), not an over-inclusive isolation violation. The corrected grouped query below fixes both the isolation violation (RoleController's total absence of scoping) and this narrower visibility gap in the same pattern, since implementation planning touches this exact code area regardless.

**Corrected grouped visibility predicate (Round 3) — the one safe pattern every row below uses.** The visibility condition "global OR current tenant" must always be its own grouped predicate, never a bare `orWhere` chained before other filters. Conceptually:

```php
Role::where(function ($q) use ($tenantId) {
        $q->whereNull('tenant_id')
          ->orWhere('tenant_id', $tenantId);
    })
    // every other filter goes OUTSIDE the closure, so it combines with AND:
    ->whereKey($id)          // or ->where('scope', $scope), ->where('name', $name), etc.
    ->first();               // or ->find($id) / ->get() / ->paginate() as appropriate
```

This produces the unambiguous SQL `(tenant_id IS NULL OR tenant_id = ?) AND <other filters>` — never the unsafe `tenant_id IS NULL OR (tenant_id = ? AND <other filters>)` that a bare, un-grouped `whereNull(...)->orWhere(...)->find($id)` chain would silently produce once `find()`'s own `WHERE id = ?` is appended after an ungrouped `orWhere`. This is not a stylistic preference — the ungrouped form is a live isolation bug: it makes **every global row visible/matchable regardless of the other filter**, because the trailing `AND id = ?` only binds to the `orWhere` branch, not the whole condition. If an existing repo scope/trait already provides an equivalent grouped-tenant-visibility helper, it should be reused instead of hand-rolling the closure — the requirement is the resulting SQL semantics, not this exact syntax.

**Design: explicit fail-closed scoping, by operation, for every `Src\RBAC` consumer that queries `Role` without an already-tenant-bound context — corrected to use the grouped predicate throughout:**

| Operation | Consumer(s) | Design |
|---|---|---|
| List (`index`, `getRolesByScope`, `PermissionMatrixService::exportToCSV`) | `RoleController::index`, `RBACController::getRolesByScope`, `PermissionMatrixService::exportToCSV` | Grouped visibility predicate (above), with `scope`/pagination filters applied outside the closure: global system roles + the caller's own tenant-owned roles; never another tenant's. `getRolesByScope`'s existing `where('scope', $scope)` must be added *after* the closure, not folded into an ungrouped `orWhere` chain. |
| Single-row read/write by ID (`show`, `update`, `destroy`, `syncPermissions`) | `RoleController::show/update/destroy/syncPermissions` | Grouped visibility predicate, then `->whereKey($id)->first()` (or equivalent) **outside** the closure — never `->find($id)` chained directly after a bare `orWhere`. A cross-tenant target then naturally falls through to each method's **already-existing** "Role không tồn tại" 404 branch — no new response code, no new branch, matching this codebase's established tenant-isolation convention (`Project::where('tenant_id', $tenantId)` in `DashboardController`/`UserControllerV2`, same "filter-then-standard-404" pattern) rather than inventing a bespoke 403. **Visibility alone is not a write authorization** — see the new global-role read/write policy below: `update`/`destroy`/`syncPermissions` must additionally reject a *found* row if it is global (`tenant_id IS NULL`), even though `show` may return it. |
| Create (`store`) | `RoleController::store` | For `scope=custom`/`scope=project`, force `tenant_id` to the authenticated request's own tenant (`$request->attributes->get('tenant_id')`) — **never** accept a client-supplied `tenant_id`, fail-closed by construction. **Corrected, Round 3 — `scope=system` is no longer permitted through this endpoint at all** (see the new global-role read/write policy below) — a tenant-scoped `POST /roles` request with `scope=system` must be rejected, not silently create a new global role with `tenant_id=null`. |
| Import (`PermissionMatrixService::importFromCSV`) | `PermissionMatrixService::importFromCSV` | The existing global-by-name `Role::where('name', $roleName)->orderByRaw(...)->first()` lookup must use the same grouped visibility predicate as single-row read/write above (its own `orderByRaw` "prefer system scope" tie-break stays outside the closure too), so a CSV import cannot silently modify another tenant's identically-named custom role's permissions. **Corrected, Round 3:** if the resolved role is global (`tenant_id IS NULL`), the import must skip/reject writing to it (same global-role read/write policy below) rather than silently syncing permissions onto a global role from a tenant-scoped import. |
| Role-assignment writes (`assignSystemRole`/`assignCustomRole`/`assignProjectRole`/`revokeRole`) | `RBACManager`, `AssignmentController` | **Corrected, Round 2 — retracted claim.** Round 1 stated these "operate on already-tenant-implicit... IDs" and were "unaffected by this section." **This was asserted, not designed, and is false as stated** — nothing in `RBACManager` or `AssignmentController` today checks that the target user, target role, or target project belong to the caller's tenant before writing an assignment row. §6a designs this properly. Note: this row is about *assigning* an existing role to a user, not mutating the role definition — §6a's rules are unaffected by the global-role read/write policy below (assigning an existing global role to a tenant's own user remains allowed, per that policy's explicit carve-out). |

**Create/update/delete/sync — global-role read/write policy (new, Round 3).** Round 2 correctly established `tenant_id IS NULL` = global/system, `tenant_id = <id>` = tenant-owned, but left the tenant-scoped `/api/v1/rbac/roles*` surface able to both **create new** global roles and **mutate existing** ones — unsafe once Option A makes this surface operational, since nothing in `rbac:role.create`/`rbac:role.edit`/`rbac:role.delete` distinguishes "manage your own tenant's roles" from "manage the platform's shared global roles."

**Decision: global/system roles are READABLE through the tenant-scoped RBAC surface, but READ-ONLY there.**

- `index`/`show`/`getRolesByScope` — may continue to include global roles in results (per the grouped visibility predicate above); this is unchanged, matches §6's decided read semantics, and is explicitly desired (a tenant needs to see which system roles exist to assign them, §6a).
- `store` — a tenant-scoped `POST /roles` request with `scope=system` must be **rejected** (e.g. HTTP 400/403 — exact code an implementation-time choice, not designed further here), not silently create a new row with `tenant_id=null`. Only `scope=custom`/`scope=project` may be created through this endpoint, always bound to the caller's own tenant (unchanged from the existing design above).
- `update`/`destroy`/`syncPermissions` — after the grouped visibility predicate resolves a row (which may legitimately be global, since `show` needs to find it too), an **additional check** before any write: if the resolved role's `tenant_id IS NULL`, reject the mutation (same 404-style fail-closed response as the existing cross-tenant branch — a global role is not "this tenant's to edit," so the response looks identical to "not found for write purposes," avoiding a data model tell). Only a role whose `tenant_id` equals the caller's own tenant may be updated, deleted, or have its permissions synced through this surface.
- `PermissionMatrixService::importFromCSV` — same rule: if CSV import resolves to a global role, it must not write to it (matches the Import row above).
- **Assignment remains distinct and is NOT restricted by this policy** — a global/system role may still be **assigned** to a user belonging to the current tenant (via `assignSystemRole`/the live `assignUserRoles` route), subject only to the existing `rbac:role.assign` permission check and §6a's fail-closed target-user check. This policy prevents a tenant caller from **modifying the global role's own definition** (its name, description, `allow_override`, or its permission set); it does not prohibit **using** an existing, unmodified global role for a user the tenant is authorized to manage.
- **No new API surface.** This design does not add a system-administration endpoint for managing global roles — if the product later needs one, that is a separately-authorized system-management surface with its own explicit authority model, out of GAP-042's scope entirely (consistent with §2d's "do not expand API surface" principle applied one level deeper).

**A real, pre-existing, evidence-confirmed DB-level constraint this design does not remove or work around:** `roles.name` carries a single-column, table-wide **`roles_name_unique`** index (confirmed at Gate 1: the rename migration explicitly renames `zena_roles_name_unique`→`roles_name_unique`, both defined on `['name']` alone, no `tenant_id`/`scope` composite). This means, as an unavoidable existing schema fact, **two different tenants cannot each create a custom role with the identical `name` string** — the second `INSERT` collides on this global unique index regardless of any application-level tenant check. This is not introduced or removed by GAP-042/Option A; it predates this defect and is out of scope to change (would be genuine, separately-authorized schema churn — a composite `(tenant_id, name)` unique index — not something this Gate 2 proposes). §10's acceptance matrix accounts for this explicitly rather than silently assuming per-tenant name-uniqueness.

**Explicitly not decided here:** whether `roles.name`'s global uniqueness should eventually become per-tenant (a genuine future schema question, out of GAP-042's boundary) — this design only ensures GAP-042's fix does not silently pretend that constraint doesn't exist.

## 6a. Tenant isolation for assignment mutations — explicit fail-closed design (new, Round 2)

**Why §6 alone was insufficient.** §6 designs read/write scoping for `Role` rows addressed *by ID*. It does not cover the separate operation of *assigning* a role to a user — a mutation that touches three potentially-cross-tenant identities at once (the target user, the target role, and, for project scope, the target project) and, per §2c, is reachable through both a live HTTP route (`assignUserRoles`/`removeUserRole`, system-scope only today) and directly through `RBACManager`'s public service methods (`assignSystemRole`/`assignCustomRole`/`assignProjectRole`/`revokeRole`) — which §2d confirms remain reachable by any current or future internal caller even though their controller wrappers (`assignSystem`/`assignCustom`/`assignProject`) stay unwired. Per the Owner's explicit instruction, the design below applies at **both** layers, so a future caller cannot bypass the boundary by invoking `RBACManager` directly instead of going through a controller.

**Design, per identity, fail-closed (reject and write nothing on any failure):**

| Identity | Rule | Applies to |
|---|---|---|
| Target user | Must belong to the authenticated caller's tenant: `App\Models\User::where('id', $userId)->where('tenant_id', $tenantId)->exists()`. No "global/system user" exception is designed here — no evidence was found anywhere in the codebase of a legitimate cross-tenant user-assignment scenario (unlike roles, which have an evidenced global-role convention, §6, users do not have an analogous documented global/shared-user concept in this codebase). If evidence for such an exception surfaces later, it requires its own explicit decision, not a silent carve-out here. | `assignSystemRole`, `assignCustomRole`, `assignProjectRole`, `revokeRole`, controller-level `assignUserRoles`/`removeUserRole` |
| Target role, system scope | Must exist and have `scope = 'system'` — closes a currently-unchecked gap: today `assignSystemRole()`/the live `assignUserRoles()` write path never verify the supplied `role_id` actually resolves to a system-scope role at all; a `custom`- or `project`-scope role id (potentially another tenant's) could currently be written into `system_user_roles` unchecked. Per §6, system-scope roles are global (`tenant_id IS NULL`) by definition, so no additional tenant check is needed once scope is confirmed. | `assignSystemRole`, controller-level `assignUserRoles` |
| Target role, custom scope | Must exist, have `scope = 'custom'`, and `roles.tenant_id` must equal the caller's tenant — a tenant may only assign its own custom roles, never another tenant's. | `assignCustomRole` |
| Target role, project scope | Must exist, have `scope = 'project'`, and `roles.tenant_id` must equal the caller's tenant (same rule as custom scope, per §6's decided tenant-ownership semantics for non-system roles). | `assignProjectRole` |
| Target project | Must exist and belong to the caller's tenant: `App\Models\Project::where('id', $projectId)->where('tenant_id', $tenantId)->exists()` — mirrors the established pattern already used elsewhere in this codebase (`ProjectController::checkProjectAccess()`, `DashboardController`). | `assignProjectRole` |
| Revoke (`revokeRole`) | Before deleting, verify the existing assignment row's `user_id` belongs to the caller's tenant (same target-user rule as above) — a delete against another tenant's assignment must not succeed, and per §6's established convention, should behave like "not found" (delete affects 0 rows) rather than revealing whether a cross-tenant row exists. | `revokeRole` |

**Where the tenant id comes from, at each layer:** controller call sites (`AssignmentController::assignSystem/assignCustom/assignProject/assignUserRoles`, `RBACController::bulkAssignRoles`) already have `$request->attributes->get('tenant_id')` available (the same mechanism `RoleController`/`RBACController::getRolesByScope` already use, §6) — this is the caller's own authenticated tenant, never client-suppliable. Per the Owner's "both controller-level AND service methods" instruction, `RBACManager`'s public assignment/revoke methods must be widened to *require* an explicit `$tenantId` parameter (e.g. `assignSystemRole(string $userId, string $roleId, string $tenantId): bool`) rather than trusting a caller to have pre-validated it — this is what makes the boundary defense-in-depth: even a caller that skips the controller's own check cannot make `RBACManager` write a cross-tenant row, because the method itself now requires and enforces `$tenantId`. This is a real, in-scope **method-signature change** (not present in Round 1's implementation surface) — recorded in §13a.

**Fail-closed means no partial writes:** every check above must complete before any `INSERT`/`UPDATE`/`DELETE` — a request that fails identity #2 (say) after having already, incorrectly, written identity #1's row is not fail-closed. Implementation must validate all applicable identities for the given scope before issuing the write, not check-then-write-then-check-more.

## 7. Governance classification / Design Dependency Preflight — updated (Round 3)

Option A's table repoint remains a **data-source repoint only** — no new business rule, no new authorization behavior, no change to the 3-layer System/Custom/Project permission-override model's *logic* (only which physical tables back it). §2b's `custom_user_roles` migration **completes** an already-designed, already-coded layer with a missing schema object — it does not introduce new business semantics either. §2d's decision to keep `assignSystem`/`assignCustom`/`assignProject`/`getEffectivePermissions` unwired is a scope-restraint decision, not a business-semantics decision. §6/§6a's tenant-scoping design (for reads/writes-by-ID and for assignment mutations, now with a corrected grouped SQL predicate and an explicit global-role read/write policy) enforces an already-evident semantic (`tenant_id IS NULL` = global, matching `RoleSeeder`'s established convention; non-null = tenant-owned) rather than inventing a new one — the Round-3 global-role read-only correction is a **security/isolation fix** (closing a write-side gap the tenant-scoping design accidentally left open), not a new business rule: it does not change who owns a role, only confirms that "own" implies "may write," which global roles by construction (`tenant_id IS NULL`, owned by no single tenant) never satisfied. Per the same reasoning GAP-040/GAP-044 used for their own test-infrastructure-only scope, **this Gate 2, as revised, still does not trigger the Design Dependency Preflight**. If implementation planning discovers evidence contradicting §2b's "preserve" decision, §6's "`tenant_id IS NULL` = global, read-only through the tenant surface" reading, or §6a's "no global-user exception" reading, work must stop and return to Gate 2, not proceed on a changed premise.
