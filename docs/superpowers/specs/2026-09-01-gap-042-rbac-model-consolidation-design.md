# GAP-042 — `Src\RBAC` Model Consolidation: Gate 2 Design

> Design-only. No code, test, migration, or deployment-configuration change is made by this document or this PR. Builds on the Owner-approved Gate 1 problem boundary (`docs/owner-decisions/GAP-042/01-request.md`): `Src\RBAC\Models\Role`/`Permission` and their direct consumers — `Src\RBAC\Services\RBACManager` and the 5 controllers in `src/RBAC/Controllers/`. The two incidental adjacent defects identified in Gate 1 (missing `AssignmentController::getUserRoles()`; the `CompensationController`/`Src\RBAC\Middleware\RBACMiddleware` constructor-wiring defect) remain explicitly out of scope.

**Revision note (Round 1).** PR #298's original submission (head `5fdcaff9779f0b81b2a26db2ec1ed29bbfb994a0`) was reviewed by the Owner and returned **CHANGES REQUESTED** — Option A remains the correct architectural direction, but the submission was not implementation-ready: it deferred the `custom_user_roles` decision instead of resolving it; it did not design tenant-isolation scoping even though Option A makes real `roles` data reachable for the first time; it did not re-audit every live route's controller→service call for contract mismatches (three genuine, previously-unknown defects were found — see §2a); and its "2-file implementation surface" claim did not separate production-behavior, schema, and test-cleanup work. This revision resolves all four points. §2, §5, §6, §7, §10, §11, §13a, §14, §15 below are revised or newly added accordingly; §1, §3, §4, §8, §9, §12 are materially unchanged (cross-references updated where section numbers shifted).

**Baseline for this design:** `origin/main @ ed8ca00b120064165f54c2ee9c8c44e946a0ef88` (re-verified via `git fetch origin`, no drift since Gate 1).

## 1. Objective

Design the smallest safe remediation that restores the live `/api/v1/rbac/*` API to production fidelity while establishing **one** authoritative RBAC data model — no split-brain between `Src\RBAC\Models\Role`/`Permission` (`zena_roles`/`zena_permissions`) and `App\Models\Role`/`Permission` (`roles`/`permissions`).

## 2b. `custom_user_roles` — explicit Gate-2 decision

**Decision: PRESERVE the 3-layer System/Custom/Project semantics. The custom layer is genuinely part of the intended design, not dead/obsolete code. Add the missing `custom_user_roles` migration, mirroring the `project_user_roles` sibling convention.**

**Evidence traced, this revision:**
- The custom layer is not a fragment — it has a complete, consistent implementation across every layer of the stack: `Role::SCOPE_CUSTOM` constant (`src/RBAC/Models/Role.php`), `UserRoleCustom` model with its own `HasSoftDeletes`/`HasAuditLog` traits and `scopeForUser`/`scopeForRole`/`scopeActive` query scopes (`src/RBAC/Models/UserRoleCustom.php`), `RBACManager::assignCustomRole()`/`getCustomPermissionsWithOverride()`/`revokeRole()`'s `'custom'` case (`src/RBAC/Services/RBACManager.php`), and a dedicated live route + controller method (`AssignmentController::assignCustom()`, `POST /api/v1/rbac/assign/custom`, correctly wired — see §2a). This is a deliberate, multi-file architectural investment, not an accidental stub.
- `computeEffectivePermissions()`'s least-privilege intersection logic (`src/RBAC/Services/RBACManager.php:53-92`) treats the custom layer as a **first-class, load-bearing** member of the 3-layer merge, not an optional add-on — the "system + custom → intersect" and "custom-only" branches are core to the algorithm, not dead branches.
- No deprecation marker, no "remove this" style comment, no superseding mechanism, and no removed/redirected route were found anywhere referencing the custom layer.
- **Countervailing evidence, honestly reported:** no frontend/UI code anywhere in `resources/` references the custom-role-assignment flow (`grep -rln "assign/custom\|assignCustomRole\|custom_user_roles" resources/` returns nothing) — the custom layer has never been exercised by an actual product feature. This is evidence of *unused-so-far*, not *obsolete-by-decision* — the repository shows no affirmative decision to retire it, only that no feature has adopted it yet. Per the Owner's stated preference ("preserve... unless evidence proves that layer is obsolete"), absence-of-adoption does not meet that bar; only an affirmative retirement decision would.

**Migration design (schema/migration category of §13a, not created in this Gate 2):** mirror `database/migrations/2026_02_02_020000_create_project_user_roles_table.php`'s shape — the closer sibling match, since `UserRoleCustom` (like `UserRoleProject`, unlike `UserRoleSystem`) uses `HasUlids`' default single `id` primary key (not a composite `[user_id, role_id]` key) and a plain nullable `deleted_at` column (not the `$table->softDeletes()` trait column `UserRoleSystem`'s migration uses):

```
Schema::create('custom_user_roles', function (Blueprint $table) {
    $table->ulid('id')->primary();
    $table->ulid('user_id');
    $table->ulid('role_id');
    $table->timestamps();
    $table->timestamp('deleted_at')->nullable();

    $table->index(['user_id']);
    $table->index(['role_id']);
    $table->foreign('user_id')->references('id')->on('users')->onDelete('cascade');
    $table->foreign('role_id')->references('id')->on('roles')->onDelete('cascade');
});
```

No `tenant_id` column — tenant scoping flows transitively through the assigned `role_id`'s own `roles.tenant_id` (§6), matching `project_user_roles`' pattern (which also carries no `tenant_id`, scoping instead through `project_id`→`projects.tenant_id`). `down()` must `dropIfExists('custom_user_roles')`, matching every sibling migration's pattern (§13).

## 3. Schema/behavioral compatibility — evidence

Both model pairs' underlying tables originate from the **same** migration (`zena_roles`/`zena_permissions` were `Schema::rename()`d to `roles`/`permissions`, not recreated) — the columns are, and always have been, physically identical except for one later addition:

| | `Src\RBAC\Models\Role` fillable | `App\Models\Role` fillable | Table columns (`roles`, current `main`) |
|---|---|---|---|
| | `name`, `scope`, `allow_override`, `description` | `name`, `scope`, `allow_override`, `description`, `is_active`, `tenant_id` | `id`, `name` (unique), `scope`, `allow_override`, `description`, `is_active`, `tenant_id`, timestamps |

| | `Src\RBAC\Models\Permission` fillable | `App\Models\Permission` fillable | Table columns (`permissions`, current `main`) |
|---|---|---|---|
| | `code`, `module`, `action`, `description` | `code`, `name`, `module`, `action`, `description` | `id`, `code` (unique), `module`, `action`, `description`, `is_active`, `name` (nullable, added `2026_01_30_000001_add_name_to_permissions_table.php`), timestamps |

`Src\RBAC\Models\Role`'s fillable set is a strict subset of `App\Models\Role`'s; same for `Permission`. Both `Permission` classes auto-generate `code` from `module`+`action` on create when empty (`Src\RBAC\Models\Permission::boot()` vs. the equivalent in `App\Models\Permission::boot()`) — identical behavior, independently implemented twice.

Pivot tables: `zena_role_permissions`→`role_permissions` and `zena_user_roles`→`user_roles` are the same rename pattern — `role_id`, `permission_id`/`user_id`, `allow_override` (role_permissions only), timestamps, composite primary key. No migration has altered `role_permissions`' or `user_roles`' columns since the rename (confirmed: only `permissions` received a post-rename column addition, per §2's migration grep). **Conclusion: the schemas are behaviorally compatible by construction — they are the same tables under different historical names, not two independently-evolved schemas that happen to look similar.**

One material behavioral difference found, not a schema difference: `RoleController::store()` (`src/RBAC/Controllers/RoleController.php:96-101`) never sets `tenant_id` on `Role::create()`, and its duplicate-name check (`Role::where('name', ...)->where('scope', ...)->exists()`) is not tenant-scoped either — role names are currently unique **globally**, not per-tenant, in the `Src\RBAC` module's own logic. This is not a regression risk from convergence — `App\Models\Role`'s `roles` table already carries the same global `roles_name_unique` index (confirmed in the rename migration, §3 of the Gate-1 evidence) — but it means neither model pair enforces per-tenant role-name uniqueness today. Convergence does not need to fix this (out of the approved boundary; flagged as a pre-existing, shared characteristic, not something Option A/B/C changes for better or worse).

## 4. Options comparison

### Option A — Converge onto canonical `roles`/`permissions`/`role_permissions`/`user_roles` (via `App\Models\Role`/`Permission`, or `Src\RBAC` classes repointed to the same tables)

**Mechanism:** Either (a) delete `Src\RBAC\Models\Role`/`Permission` and have `src/RBAC/Controllers/*`/`RBACManager`/`PermissionMatrixService` use `App\Models\Role`/`Permission` directly, or (a′) keep the `Src\RBAC\Models\Role`/`Permission` class names (so no `use` statement churn across 9+ consumer files) but change `protected $table` from `zena_roles`/`zena_permissions` to `roles`/`permissions`, and change the two hardcoded pivot-table strings in `Role::permissions()`/`Permission::roles()` from `zena_role_permissions` to `role_permissions` (already what `Src\RBAC\Models\RolePermission` — currently dead — declares). `UserRoleSystem`/`UserRoleCustom`/`UserRoleProject`'s `role()` relation needs no change if `Role::class` still resolves within `Src\RBAC\Models` — it would just point at the now-repointed table.

**Pros:** Zero new tables, zero new migrations for `Role`/`Permission`/`role_permissions`/`user_roles` (schema already exists, already seeded, already the live source of truth for the `rbac:` authorization gate itself). Smallest possible diff — 2 model files' `$table`/pivot-string values, no controller/service logic changes required (fillable subset means no field ever gets silently dropped). Immediately closes the split-brain: one authoritative table set, used by both the authorization gate and the business logic behind it. Matches the already-existing-but-dead `RolePermission` pivot model's stated intent.

**Cons:** `Src\RBAC\Models\Permission`'s fillable (`code, module, action, description`) omits `name`, which `App\Models\Permission`'s callers may rely on being settable; since `permissions.name` is nullable (added later, per §3), this is a non-breaking gap, not a conflict — existing `Src\RBAC`-created rows simply leave `name` null, exactly as `PermissionSeeder`'s own rows already sometimes do (this is the AUD-28 pattern GAP-044 already documented, not a new risk). `custom_user_roles` needs its own migration regardless of this option — resolved at §2b, not a cost specific to Option A.

### Option B — Thin compatibility/adapter layer, `Src\RBAC` classes/API preserved as-is against the standard schema

**Mechanism:** Same table repointing as Option A, but additionally wrap `Src\RBAC\Models\Role`/`Permission` in an explicit adapter (e.g., extend `App\Models\Role`/`Permission` instead of `Illuminate\Database\Eloquent\Model` directly, remapping the narrower `Src\RBAC` fillable/constant surface — `Role::VALID_SCOPES`, `Permission::generateCode()` — onto the parent).

**Pros:** Slightly more explicit "this is the same underlying entity, different historical API" statement in code; a single class hierarchy point if the two APIs need to diverge again later for some reason.

**Cons:** More moving parts than Option A for no behavioral difference given §3's finding that the fillable sets are already a strict subset — inheritance adds a coupling axis (any future change to `App\Models\Role` silently propagates to `Src\RBAC\Models\Role`) without buying anything Option A's direct table-repoint doesn't already achieve. Effectively Option A with extra indirection; **not recommended as a separate mechanism** unless Gate 2 review surfaces a concrete reason the two APIs must diverge.

### Option C — Retire/de-duplicate `Src\RBAC` model/service path entirely, route `/api/v1/rbac/*` through `App\Models\Role`/`Permission` directly

**Mechanism:** Delete `Src\RBAC\Models\Role`/`Permission`/`RolePermission`; rewrite the 5 controllers + `PermissionMatrixService` to use `App\Models\Role`/`Permission` and `App\Models\User::roles()`/`hasPermission()` instead of `RBACManager`'s 3-layer computation; decide the fate of `RBACManager`'s system/custom/project layering (either port it to operate against `App\Models\Role` + the existing `system_user_roles`/`project_user_roles` tables plus a new `custom_user_roles` migration, or drop the 3-layer model in favor of `App\Models\User`'s flat `roles()`/`hasPermission()`).

**Pros:** Eliminates the duplicate class hierarchy entirely — no `Src\RBAC\Models\Role` vs `App\Models\Role` naming confusion for future readers. Removes the now-dead `App\Http\Controllers\{RoleController,PermissionController,AssignmentController,RBACController}` / `App\Services\{RBACManager,PermissionMatrixService}` orphan-duplicate question too, if folded into the same cleanup (though that cleanup is explicitly **not** part of GAP-042's approved boundary, per Gate 1 — see §7).

**Cons:** By far the largest diff of the three — touches every consumer file's imports and internals, not just 2 models' table pointers; the 3-layer System/Custom/Project permission-override model (`RBACManager::computeEffectivePermissions()`, §2 of the Gate-1 evidence, §2 above) is materially richer than `App\Models\User`'s flat `hasRole()`/`hasPermission()` (least-privilege intersection across layers, `allow_override` per layer) — collapsing it to the flat model is a **behavior change**, not a bug fix, and is exactly the kind of business-semantics decision the repository's Design Dependency Preflight exists to catch (§7). Rewriting 5 controllers + a service class carries materially more regression risk than repointing 2 `$table` properties, for a benefit (naming clarity) that Option A's dead-code note (`RolePermission` already unused) shows can be achieved incrementally later without forcing the whole rewrite now.

### Legacy-compatibility-table/view variant (evaluated, not recommended)

Recreating `zena_roles`/`zena_permissions` as either permanent duplicate tables (kept in sync with `roles`/`permissions` via triggers/observers) or database views over `roles`/`permissions` was evaluated per the Owner's explicit request to consider it. **Not recommended:**
- A duplicate table reintroduces exactly the split-brain authority problem Gate 1 diagnosed (two tables, one truth, requiring a sync mechanism that can itself drift) — the opposite of the Owner's stated goal ("establishing ONE authoritative RBAC data model... Avoid split-brain RBAC data").
- A read-only view could serve `SELECT`-only consumers, but `Src\RBAC\Controllers\RoleController::store/update/destroy`, `PermissionController::store/update/destroy`, and `RBACManager`'s role-assignment methods (§2) all write — a view does not support arbitrary writes back to a renamed base table without additional (and MySQL-version-sensitive) `INSTEAD OF`-trigger machinery Laravel's schema builder does not manage, adding operational complexity with no compatibility benefit Option A doesn't already provide directly.
- No consumer in the approved boundary (§2) requires the literal string `zena_roles`/`zena_permissions` to exist for any reason other than that being the currently-hardcoded (and broken) table name — i.e., nothing needs the *name* `zena_roles`, only working Role data. A compatibility shim solves a problem no live consumer actually has.

### Recommendation: **Option A** (direct table repoint, keeping `Src\RBAC\Models\Role`/`Permission` class names to minimize consumer-file churn)

Rationale: §3 establishes the schemas are the same tables historically, not independently-evolved ones — there is nothing to "adapt" (Option B) or "port behavior across" (Option C) that Option A's direct repoint doesn't already carry for free, because the fillable/relationship surface is already a compatible subset. Option C's larger rewrite is justified only if the Owner separately decides to collapse the 3-layer permission model into the flat one — a business-semantics decision this Gate 2 does not make (§7) and that the Gate-1-approved boundary did not ask for. Option A is reversible (§13), requires no new migration for the primary defect (§11), and directly satisfies "avoid split-brain" by making `roles`/`permissions` the single table set for both the authorization gate and the business logic behind it, on day one. (§2a's contract fixes and §2b's `custom_user_roles` migration and §6's tenant-scoping design are additional, separately-tracked work items within the same approved boundary — see §13a — not alternate options to Option A itself.)

## 5. API compatibility for `/api/v1/rbac/*` — corrected, honest restoration claim (Round 1)

Option A itself changes zero route signatures, zero request/response shapes, zero controller method bodies (only the two models' `$table`/pivot-string values change) — every one of the ~20 routes in `src/RBAC/routes/api.php` keeps its existing URL, HTTP verb, request validation, and JSON response shape.

**Corrected per Owner Correction 3 — Option A alone does NOT restore the whole live RBAC surface.** Of the ~20 routes:

- **Restored to working (200/403 as appropriate) by Option A alone:** `RoleController`'s CRUD + `syncPermissions` (subject to §6's tenant-scoping fix landing in the same implementation, since these are the exact methods §6 designs against), `PermissionController`'s CRUD, `RBACController::getRolesByScope`/`getPermissionHierarchy`/`getAuditLog`, `PermissionMatrixController`'s export/import/validate/template (subject to §6's scoping fix for `PermissionMatrixService::exportToCSV`/`importFromCSV`), `AssignmentController::assignSystem`/`assignCustom`/`assignProject`/`getEffectivePermissions`/`assignUserRoles`/`removeUserRole`.
- **NOT restored by Option A alone — requires §2a's separate, additionally-designed fixes:** `RBACController::getUserEffectivePermissions`/`checkUserPermission` (undefined-method fatals, §2a #1-#2), `bulkAssignRoles`' project-scope branch (silent false-success, §2a #3), and three `assignments/projects/*` routes (undefined-method fatals, §2a #4-#6).
- **Remains excluded per Owner instruction, unfixed, unregistered under GAP-042:** `assignments/users/{user}/roles` GET (`getUserRoles`, Gate 1's original incidental finding), and the `CompensationController`/`Src\RBAC\Middleware\RBACMiddleware` constructor-wiring defect (unrelated controller, outside this boundary).

This document does **not** claim "the whole live RBAC surface is restored" — it claims Option A restores the table-rename-caused failures, and §2a additionally designs (without yet implementing) fixes for the three newly-found, table-rename-independent contract defects that sit inside the same approved boundary. §13a's implementation surface keeps these as a distinct, explicitly-scoped category so implementation planning cannot silently conflate "table repoint done" with "route restored."

## 6. Tenant isolation and tenant_id semantics — corrected, explicit fail-closed design (Round 1)

**Why this could not stay deferred.** `tenant.isolation` middleware (`app/Http/Middleware/TenantIsolationMiddleware.php`) only establishes *authenticated tenant context* (`$request->attributes->set('tenant_id', ...)`) — it does not automatically scope any model query. Every `/api/v1/rbac/*` route additionally runs `rbac:<code>` (`RoleBasedAccessControlMiddleware`), which only checks *whether the user holds a named permission* — it never inspects *which row* a request targets. Neither middleware bounds `Role::query()`, `Role::find($id)`, or `Role::where(...)` to the caller's own tenant. **Today, on current `main`, this is unreachable — every such query 500s before returning any row, because the table doesn't exist.** Once Option A repoints the table, these same queries **succeed** against real, tenant-owned data — so the cross-tenant exposure becomes newly, actually reachable for the first time. This is exactly the case the Owner's correction identifies: fixing the table-name defect without fixing the scoping would trade an availability defect for a confidentiality defect.

**Intended semantics, traced from evidence (not invented):**
- `roles.tenant_id` is nullable. `RoleSeeder`'s `system`-scope roles (the only roles any production code path has ever created — confirmed by `grep -rn "Role::create\|Role::firstOrCreate"` across `app/`, `src/`, `database/`, none of which ever sets `tenant_id`) are created with `tenant_id` left `null`. This is decisive evidence for the intended meaning: **`tenant_id IS NULL` = global/system role, visible to and usable by every tenant; `tenant_id = <id>` = a role owned by exactly that tenant** (the `custom`/`project` scopes' evident purpose, per `Role::VALID_SCOPES` and `RoleController::store()`'s validation, even though no code has yet exercised non-null `tenant_id` in practice).
- `RBACController::getRolesByScope()` (`src/RBAC/Controllers/RBACController.php:128`) already implements a *partial* version of this: `if ($tenantId) { $query->where('tenant_id', $tenantId); }` — evidence the tenant-scoping intent already exists in this exact codebase, inside the approved boundary, just inconsistently applied (only this one of the module's several list/read paths does it, and even this one has a related, narrower gap noted below). `permissions` has no `tenant_id` column in either schema — permissions remain global/module-scoped in both systems, unchanged by this design.
- **A related, narrower gap in the existing partial implementation, noted but not the primary fix target:** `getRolesByScope()`'s filter, as written, is `WHERE tenant_id = ?` when a tenant is present — under standard SQL null semantics this *excludes* global (`tenant_id IS NULL`) system roles once any tenant context is set, an under-inclusive visibility gap (a tenant using this endpoint currently cannot see system roles), not an over-inclusive isolation violation. §6's corrected query below (`whereNull('tenant_id')->orWhere('tenant_id', $tenantId)`) fixes both the isolation violation (RoleController's total absence of scoping) and this narrower visibility gap in the same pattern, since implementation planning touches this exact code area regardless.

**Design: explicit fail-closed scoping, by operation, for every `Src\RBAC` consumer that queries `Role` without an already-tenant-bound context:**

| Operation | Consumer(s) | Design |
|---|---|---|
| List (`index`, `getRolesByScope`, `PermissionMatrixService::exportToCSV`) | `RoleController::index`, `RBACController::getRolesByScope`, `PermissionMatrixService::exportToCSV` | `Role::whereNull('tenant_id')->orWhere('tenant_id', $tenantId)` (global system roles + the caller's own tenant-owned roles; never another tenant's) |
| Single-row read/write by ID (`show`, `update`, `destroy`, `syncPermissions`) | `RoleController::show/update/destroy/syncPermissions` | Prepend the same `whereNull('tenant_id')->orWhere('tenant_id', $tenantId)` constraint before `find($id)` (i.e. `Role::whereNull('tenant_id')->orWhere('tenant_id', $tenantId)->find($id)` or equivalent). A cross-tenant target then naturally falls through to each method's **already-existing** "Role không tồn tại" 404 branch — no new response code, no new branch, matching this codebase's established tenant-isolation convention (`Project::where('tenant_id', $tenantId)` in `DashboardController`/`UserControllerV2`, same "filter-then-standard-404" pattern) rather than inventing a bespoke 403 |
| Create (`store`) | `RoleController::store` | For `scope=custom`/`scope=project`, force `tenant_id` to the authenticated request's own tenant (`$request->attributes->get('tenant_id')`) — **never** accept a client-supplied `tenant_id`, fail-closed by construction. For `scope=system`, `tenant_id` stays `null` (matching `RoleSeeder`'s established convention) — creating a `system`-scope role is already gated by the existing `rbac:role.create` permission check at the route level; this design adds no new permission code, only closes the missing tenant assignment |
| Import (`PermissionMatrixService::importFromCSV`) | `PermissionMatrixService::importFromCSV` | The existing global-by-name `Role::where('name', $roleName)->orderByRaw(...)->first()` lookup must be scoped the same way as single-row read/write above, so a CSV import cannot silently modify another tenant's identically-named custom role's permissions |
| Role-assignment writes (`assignSystemRole`/`assignCustomRole`/`assignProjectRole`) | `RBACManager` | Unaffected by this section — these operate on already-tenant-implicit user/role/project IDs supplied by the caller, not on an unscoped `Role::query()`; §2a's argument-order/undefined-method defects for these call sites are the actual risk, already designed there |

**A real, pre-existing, evidence-confirmed DB-level constraint this design does not remove or work around:** `roles.name` carries a single-column, table-wide **`roles_name_unique`** index (confirmed at Gate 1: the rename migration explicitly renames `zena_roles_name_unique`→`roles_name_unique`, both defined on `['name']` alone, no `tenant_id`/`scope` composite). This means, as an unavoidable existing schema fact, **two different tenants cannot each create a custom role with the identical `name` string** — the second `INSERT` collides on this global unique index regardless of any application-level tenant check. This is not introduced or removed by GAP-042/Option A; it predates this defect and is out of scope to change (would be genuine, separately-authorized schema churn — a composite `(tenant_id, name)` unique index — not something this Gate 2 proposes). §10's acceptance matrix accounts for this explicitly rather than silently assuming per-tenant name-uniqueness.

**Explicitly not decided here:** whether `roles.name`'s global uniqueness should eventually become per-tenant (a genuine future schema question, out of GAP-042's boundary) — this design only ensures GAP-042's fix does not silently pretend that constraint doesn't exist.

## 7. Governance classification / Design Dependency Preflight — updated (Round 1)

Option A's table repoint remains a **data-source repoint only** — no new business rule, no new authorization behavior, no change to the 3-layer System/Custom/Project permission-override model's *logic* (only which physical tables back it). §2b's `custom_user_roles` migration **completes** an already-designed, already-coded layer with a missing schema object — it does not introduce new business semantics either (the semantics — a `custom`-scope role layer, least-privilege-intersected with system/project — already exist in shipped `RBACManager` code; the migration only makes the existing code path executable). §6's tenant-scoping design enforces an already-evident semantic (`tenant_id IS NULL` = global, matching `RoleSeeder`'s established convention; non-null = tenant-owned) rather than inventing a new one, and closes a fail-open gap without changing what "owns" a role. Per the same reasoning GAP-040/GAP-044 used for their own test-infrastructure-only scope (and the Gate-1 evidence's own governance classification), **this Gate 2, as revised, still does not trigger the Design Dependency Preflight** — no canonical business-domain semantics are being invented; §2b and §6 both make existing, evidenced-but-incompletely-implemented semantics actually work, not decide new ones. If implementation planning discovers evidence contradicting §2b's "preserve" decision or §6's "`tenant_id IS NULL` = global" reading, work must stop and return to Gate 2, not proceed on a changed premise.

## 10. Required acceptance design (Gate 3 verification criteria — not built at Gate 2) — strengthened (Round 1)

All of the following must **fail on current `main`** (proving they actually test the defect) and **pass only after the eventual Option A + §2a + §2b + §6 remediation**:

1. **Clean genuine MySQL 8.0 bootstrap, no PHPUnit schema shim.** A CI job (or a documented, exactly-reproducible manual procedure equivalent to Gate 1's disposable-container method) that runs `php artisan migrate:fresh` (including the new `custom_user_roles` migration, §2b) against a real MySQL 8.0 instance with `ensureSqliteZenaRbacTables()` already deleted from `tests/TestCase.php`, and independently inventories the resulting tables.
2. **Assertion that the application does NOT require `zena_roles`/`zena_permissions`.** A direct check (e.g. `SHOW TABLES LIKE 'zena_roles'` / `'zena_permissions'` returning empty) run against that same clean schema — the negative-space proof, not just a positive proof that `roles`/`permissions` work.
3. **Authenticated + authorized real `/api/v1/rbac/roles` and `/permissions` HTTP paths succeed.** A real HTTP request (not a facade/internal call) with valid Sanctum auth, valid tenant header, and a real, granted `role.view`/`permission.view` permission on `App\Models\Permission`, against the clean schema, must return HTTP 200 with real data — the same request shape Gate 1's evidence used to prove the current HTTP 500.
4. **Denied access remains denied.** The same requests, with a user lacking the required permission, must still return HTTP 403 through the unaffected `rbac:<code>` gate — proving convergence did not accidentally loosen authorization.
5. **Tenant A cannot list, show, update, delete, or sync-permissions on tenant B's role.** Discriminating, not just absence-of-regression: create tenant A + tenant B, each with their own `custom`-scope role (distinct names, per §6's documented `roles_name_unique` constraint); as an authenticated, authorized tenant-B user, attempt `GET /roles` (must not list A's role), `GET /roles/{a_role_id}` (must 404), `PUT /roles/{a_role_id}` (must 404, and the row must be verified unchanged by an independent query), `DELETE /roles/{a_role_id}` (must 404, row must still exist), `POST /roles/{a_role_id}/permissions` sync (must 404, permissions must be verified unchanged). A global `system`-scope role, by contrast, must remain visible/listable to both tenants.
6. **Role creation binds to the authoritative tenant per §6's decided semantics.** `POST /roles` with `scope=custom` as an authenticated tenant-A user, even if the request body attempts to supply a different `tenant_id`, must create a row whose `tenant_id` is verifiably tenant A's own (server-derived, not client-supplied) — proving the fail-closed binding, not just its absence of visible symptoms.
7. **`effective-permissions`/`check-permission` live routes no longer fail on missing tables or a service-contract mismatch.** `GET /api/v1/rbac/users/{user}/effective-permissions` and `POST /api/v1/rbac/users/{user}/check-permission` must return HTTP 200 with correct data (not the `Error`-not-`Exception` uncaught fatal documented in §2a #1-#2) — this specifically exercises the corrected `RBACController`↔`RBACManager` method-name/argument contract, not just the table repoint.
8. **System/Custom/Project permission computation works per the preserved 3-layer semantics.** A user with a `system`-scope role only, a user with `system`+`custom` roles (asserting the least-privilege intersection plus `allow_override` behavior documented in `RBACManager::computeEffectivePermissions()`), and a user with a `project`-scope role for a specific project, each verified via `RBACManager::calculateEffectivePermissions()`/the live `effective-permissions` route — proving §2b's decision is not just "table exists" but "the layer computes correctly."
9. **The `custom_user_roles` decision is proven on genuine MySQL, not merely asserted.** `RBACManager::assignCustomRole()` writes a row to `custom_user_roles` on real MySQL 8.0 and `getCustomPermissionsWithOverride()` reads it back correctly (join through `role.permissions` succeeds) — the specific, previously-nonexistent-table path from §2b, live-verified, not just schema-inventoried.
10. **Representative assignment paths write to the intended canonical assignment tables.** At minimum: `POST /assign/system` → verified row in `system_user_roles`; `POST /assign/custom` → verified row in `custom_user_roles`; `POST /assign/project` → verified row in `project_user_roles`; `POST /roles/{role}/permissions` sync → verified rows in `role_permissions` — each via an independent query, not `zena_*`, and each specifically checking the *correct* table for *that* assignment scope (proving no cross-wiring, relevant given §2a #3's argument-order finding).

12. **No test-only shim can manufacture production-impossible RBAC schema.** The test class(es) implementing 1-11 above must not extend `Tests\TestCase` in a way that still has access to the now-deleted `ensureSqliteZenaRbacTables()`/`zena_ddl_bootstrap` shim, or must otherwise be structurally incapable of silently recreating `zena_roles`/`zena_permissions` — this is the direct discriminating check that closes the exact masking mechanism Gate 1's §5e demonstrated, extended to cover that `custom_user_roles`' new migration is a real migration (checked into `database/migrations/`), not another test-only bootstrap helper.
